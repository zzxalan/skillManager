# ZNMZDX 案例提炼

## 案例事实

`smart-znmzdx-mixed` 为客户专属 mixed 插件，交付内容包括定制设备控制 H5、跨插件设备能力编排、原应用入口替换、插件包集成以及 Mock/现场分层验证。仓库保留了需求、设计、数据归属、计划、验证和 PR 说明，可作为本 skill 的真实来源。

关键做法：

- 撤回曾放入 `smart-core` 的单客户定制能力，改由客户插件承担。
- 通过插件生命周期管理的全局拦截器接管宿主和小程序各自使用的应用列表入口。
- 继续使用宿主服务完成应用权限过滤，只替换目标 H5 的 `path`。
- 保留小程序原签名校验，并用仅 Servlet 内部转发可设置的请求属性保护免登录内部接口，避免重复消费 nonce 和外部直连。
- 通过宿主 MAIN Bean 和其他插件正式 Supplier/接口读取空间、设备、门锁和班牌能力，不建影子表、不跨插件写表。
- 用独立 Vite H5 构建生成 `dist/h5`，再由后端打包到插件 JAR 的 `web/h5`。
- 首次渲染前同步宿主设置和账号权限，把主题 token 写到根 CSS 变量，使挂到 `body` 的移动端弹层也跟随主题。
- 把 Mock 回归与 live 安全用例分开；真实门锁、密码、班牌和空开操作没有单独授权时明确跳过并记录原因。

## 迭代暴露的通用问题

后续提交不是简单视觉微调，而是暴露了定制项目最容易遗漏的契约边界：

- 前端显示在线、后端却把 `unknown` 当离线，说明跨插件状态语义必须统一。
- 密码空对象、残缺对象、无权限和读取失败不能都显示“未设置”。
- H5 不能只依赖浏览器缓存权限，独立入口需要主动加载宿主权威权限。
- 同类型设备需要消费接口已有具体名称，避免前端只显示类型名。
- 临时密码的有效期属于已有契约字段，应优先消费现有字段，不为展示新增重复数据。
- 客户端实际使用的入口可能与管理端不同；只改 `GET /api/apps` 未覆盖小程序 `POST /api/third-party/apps`。

这些问题共同形成三条规则：先确认真实调用链，再确认数据/权限/状态语义，最后按客户端入口逐条验证。

## 不应泛化的案例常量

以下内容只属于 ZNMZDX，不得复制为其他客户默认值：

- plugin id、包名、中文客户名和 `/child/znmzdx/...` 路径。
- “空间管理 / 设备控制”的目标分组、应用名称和插件 ID。
- `door:password:add`、具体房间数据范围和门锁密码页面规则。
- 具体设备类型、厂商控制链路、现场账号、IP、端口和环境数据。
- 采用全局拦截器这一实现选择；新项目若已有正式扩展点，应优先使用扩展点。

## 适用结论

本案例足以支持一个独立客户定制 skill，因为它覆盖了通用项目工作流未展开的四个专属问题：客户差异隔离、原入口契约保护、停用即回退、现场高风险验证分层。具体代码样式仍由 smart 后端/前端 standards 负责。
