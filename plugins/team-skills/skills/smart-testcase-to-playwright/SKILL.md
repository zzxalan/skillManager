# Smart Testcase To Playwright

## Goal

把飞书链接或 Excel 文件中的 smart 测试用例转换为可重复执行、可输出结果并经过实际验证的 Playwright 测试。测试代码必须写入主要业务归属插件根目录的 `test/`，不得只返回聊天中的代码片段。

## Trigger Boundary

- 仅在用户明确写出 `$smart-testcase-to-playwright` 或明确要求“调用 smart-testcase-to-playwright skill”时执行。
- 不因用户普通提到测试用例、飞书、Excel、浏览器或 Playwright 自动触发。
- 只服务 smart 基座和 `smart-*` 插件的 Web 管理端测试；Android 终端、微信小程序和非 smart 系统不在范围内。

## Core Workflow

### 1. 读取并标准化测试用例

1. 确认输入是以下一种来源：
   - 可访问的飞书链接。
   - 本地或附件形式的 `.xlsx`、`.xls` 文件。
2. 同时提供飞书和 Excel 时，不要默认合并；先确认哪个是权威版本，或者用户是否要求对比。
3. 处理飞书链接时，优先使用可用的飞书连接器；没有适用连接器时，再使用已有登录态的浏览器或 Chrome。不要要求用户复制可直接读取的正文。
4. 处理 Excel 时，使用电子表格能力只读分析工作簿；扫描全部工作表，保留工作表名和原始行号，不修改源文件。
5. 读取 `references/testcase-normalization.md`，将不同来源统一为标准用例模型。
6. 缺少操作步骤或预期结果时暂停生成并询问；其他非关键缺失项可以记录明确假设后继续。

### 2. 检查执行条件

检查并尽量从文档、代码和环境中自行确认：

- 测试环境前端、后端地址以及环境性质。
- 用例要求的账号角色、菜单权限和数据权限。
- 目标插件是否安装、启用并可访问。
- 测试数据是已有数据、脚本创建还是接口准备。
- 本机 Node.js、项目包管理器和 Playwright 浏览器是否可用。
- 对应插件仓库及其 `AGENTS.md`、现有 `test/`、包管理器和代码风格。

仅把真正阻止执行的问题集中询问用户。不得在生产、客户现场或性质不明的环境运行。普通测试环境执行已获授权，但涉及真实设备、外部消息、批量操作或其他高影响副作用时仍需单独确认。

### 3. 定位代码归属

1. 使用 `$smart-platform` 通过 MCP，根据用例模块、plugin id、菜单或业务名称确定主要业务插件。
2. 再检查本地实际仓库结构；项目地图与代码冲突时，以代码为准并说明差异。
3. 使用以下放置规则：
   - 单插件用例：写入该插件根目录的 `test/`。
   - 跨插件流程：写入主要业务发起方或业务数据归属插件的 `test/`。
   - 一份来源包含多个独立插件：按插件拆分到各自的 `test/`。
   - 无法判断主要归属：先询问，不得默认放入 `smart-core-mixed`。
4. 发现 `test/` 已存在时，沿用现有结构和依赖，不覆盖用户已有配置。

### 4. 准备可复用登录态

1. 使用 `$smart-token-login` 获取测试环境 token，并遵守其环境确认和脱敏规则。
2. 区分两种登录态：
   - 浏览器探索所需的当前会话。
   - Playwright 后续每次执行都能重建的认证状态。
3. 不把真实 token、账号密码或数据库密码写入源码、报告、截图说明或版本库。
4. 让生成的测试从 `.env` 或运行时环境变量读取凭据，使用 `auth.setup.ts` 生成 `.auth/user.json`。
5. 优先使用账号密码调用 smart 登录接口；仅传入 `SMART_TOKEN` 时允许直接注入 token。
6. 遇到初始密码重置、验证码规则变化、账号失效或权限不足时暂停并报告，不要绕过业务权限。

### 5. 探索真实测试路径

1. 在目标测试环境打开浏览器并完成登录。
2. 按标准化用例逐步操作，确认菜单入口、路由、弹窗、表格、表单、异步加载、上传下载和结果状态。
3. 记录稳定定位器、每一步的可观察结果以及必要的数据准备和清理动作。
4. 文档步骤与实际系统不一致时，先区分是文档过期、环境差异还是产品缺陷；不要静默改写用例意图。
5. 无法稳定定位元素时，优先寻找语义定位器；仍不可行时记录需要补充的 `data-testid`，不要用脆弱的长 XPath 掩盖问题。

### 6. 生成 Playwright 工程和用例

1. 读取 `references/playwright-implementation.md`。
2. 新建 `test/` 时复制 `assets/playwright-template/` 的内容；再根据实际插件、环境和用例补充测试文件。
3. 如果项目已有 Playwright 工程，只补充所需配置、认证 fixture 和测试，不整体替换。
4. 默认生成 TypeScript，测试文件使用 `<feature>.spec.ts` 命名。
5. 在测试标题中保留原始用例编号，并通过注释或 `test.info().annotations` 保留飞书链接或 Excel 的“文件名/工作表/行号”。
6. 将每个预期结果落实为对应断言；不要只断言页面打开或元素存在。
7. 为重复执行设计唯一测试数据、准备逻辑和清理逻辑；不得依赖上一次测试留下的状态。

### 7. 安装、执行和修正

1. 在插件根目录的 `test/` 中使用项目惯用包管理器安装依赖。
2. 必要时安装 Chromium，但不要擅自升级或改写插件其他模块的依赖。
3. 先执行类型检查，再执行目标测试；首次探索可使用 headed 模式，最终至少完成一次正常模式运行。
4. 根据真实失败修正定位器、等待条件、测试数据和断言，不用固定休眠掩盖竞态问题。
5. 运行完成后确认以下产物存在：
   - `playwright-report/` HTML 报告。
   - `test-results/results.json`。
   - `test-results/junit.xml`。
   - 失败时的截图、视频或 trace。
6. 因环境、权限或产品缺陷无法通过时，保留证据并明确标记“已生成但未完成运行验证”，不得宣称验证成功。

## Safety

即使在测试环境，执行以下动作前也要单独确认：

- 门禁开锁、IoT 或其他真实设备控制。
- 公告、信发、短信、邮件、微信或第三方平台消息发送。
- 批量删除、批量审批、批量同步和大范围数据重置。
- 触发定时任务、第三方抓取、外部数据同步或不可逆流程。
- 处理真实人脸、个人信息或其他敏感数据。

优先使用专用测试数据、模拟目标或可回滚操作。只执行测试用例明确要求且已确认范围内的动作。

## Delivery

最终交付必须说明：

- 输入来源及解析出的用例数量。
- 用例到 smart 插件和测试文件的映射。
- 新增或修改的 `test/` 文件路径。
- 执行命令、通过/失败/跳过数量和报告路径。
- 使用的环境、账号角色和数据准备方式，敏感值必须脱敏。
- 未满足的前置条件、做出的假设、产品缺陷或未完成验证项。

## Resources

- 解析飞书或 Excel 测试用例时读取 `references/testcase-normalization.md`。
- 生成、执行和审查 Playwright 测试时读取 `references/playwright-implementation.md`。
- 新建独立测试工程时复制并调整 `assets/playwright-template/`；不要把模板原样覆盖到已有 `test/`。
